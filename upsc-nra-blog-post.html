Executive Summary (TL;DR)

During an independent security assessment of the UPSC NRA Candidate Portal, I identified 15+ vulnerabilities across 4 severity levels — including 3 CRITICAL findings capable of mass PII exfiltration of Aadhaar numbers, biometrics, DigiLocker documents, and financial records for millions of candidates. All findings were responsibly reported to CERT-In and UPSC before any public disclosure. The portal has since been patched.

🕵️ How I Found It #

The entry point was a 14.6MB Angular production bundle — main.375ee5cb2feed08e.js. Angular apps ship their entire source in minified JS that runs in the browser. With a JS formatter and a bit of patience, the full application logic including API routes, cryptographic functions, and hardcoded secrets becomes readable.

Tools of the Trade
Browser DevTools curl Python (Requests + PyCryptodome) JS Pretty-Printer grep / findstr

🔴 Critical Findings #

V-01 CVSS 9.8

RSA-2048 Private Key Exposed in Production JS

The application used RSA-PKCS1-v1.5 encryption for all sensitive API communication — including Aadhaar demographic data, salt values, and credential material. The private key used to decrypt server responses was embedded in plaintext inside the frontend JavaScript bundle. This means anyone who downloaded the JS file (it's public, no auth needed) had the decryption key for all encrypted server traffic. 

// Functions found in JS bundle:
function encryptToServer(data) {
    return pki.publicKeyFromPem(RSA_PUBLIC_KEY).encrypt(data, "RSAES-PKCS1-V1_5")
}
function decryptFromServer(data) {
    return pki.privateKeyFromPem(RSA_PRIVATE_KEY).decrypt(atob(data), "RSAES-PKCS1-V1_5")
}

The RSA key pair (both public and private) was hardcoded as string constants — shipped to every visitor's browser.

Impact:

Complete compromise of transport-layer encryption. Any intercepted API response could be decrypted. Any request could be forged with valid signatures.

V-02 CVSS 9.4

DigiLocker OAuth Client Credentials Exposed

DigiLocker is India's official digital document wallet — linked to citizens' Aadhaar, PAN card, driving licence, and more. The UPSC portal integrated with DigiLocker to verify candidate documents. The OAuth CLIENT_ID and CLIENT_SECRET for this DigiLocker integration were hardcoded in the JS bundle. 

CLIENT_ID:     0ca22ccc84c7c9f9811e47f8********
CLIENT_SECRET: c05e91cb548ec3434c4048d8********
Impact:

An attacker could use these credentials to impersonate the UPSC portal to DigiLocker — potentially gaining access to any candidate's Aadhaar, PAN, and driving licence via the DigiLocker OAuth flow. These are production credentials for a government-to-government API.

V-03 CVSS 9.4

IDOR — Mass PII Exfiltration

Multiple candidate data endpoints accepted sequential numeric identifiers and did not enforce authorization checks against the requesting user's session. The vault endpoint is the most sensitive — it stores Aadhaar UID and eKYC data. With a valid session token (obtainable via normal registration), incrementing the ID parameter exposed other candidates' complete profiles. 

GET /ngrp_api/getfullprofile/Candidate/FullProfile/GetFUllProfile/{id}
GET /ngrp_api/Candidate/V2/Profile/Get/{id}
GET /ngrp_api/vault/V2/Register/{id}
GET /ngrp_api/admin_api/Get_eAdmitCard/{id}
Impact:

With a valid session token and a script, bulk exfiltration of PII for millions of UPSC NRA candidates was technically feasible via sequential enumeration.

V-04 CVSS 9.1

Aadhaar Demo Auth API Exposed

The portal integrated with UIDAI's Aadhaar Demo Authentication API to verify candidate identity. These endpoints were accessible from the frontend and — critically — the demoauth endpoints revealed their expected request schema via error responses when called without authentication. 

// Confirmed response (HTTP 422) from /ngrp_api/aadhar/otp/generate-otp-demoauth/:
{
  "detail": [
    {"type": "missing", "loc": ["body", "consent"], "msg": "Field required"},
    {"type": "missing", "loc": ["body", "name"], "msg": "Field required"},
    {"type": "missing", "loc": ["body", "gender"], "msg": "Field required"},
    {"type": "missing", "loc": ["body", "dob"], "msg": "Field required"},
    {"type": "missing", "loc": ["body", "applicantID"], "msg": "Field required"}
  ]
}
Impact:

The endpoint was reachable, and the error response documented the exact request body needed. Combined with V-01 (RSA key) and V-03 (IDOR for applicantIDs), this created a full attack chain for Aadhaar eKYC data extraction.

V-05 CVSS 8.9

Admin Portal — Zero Rate Limiting

The admin portal login at /access-block-com used a separate auth flow with RSA-encrypted credentials. The endpoint had zero rate limiting. I ran 650+ authentication attempts against it with no lockout, no CAPTCHA, and no throttling response. 

login() {
    const encEmail = btoa(stringToBytes(this.email));
    const encMobile = btoa(stringToBytes(this.mobile));
    this.http.post(API_URL + "access-login/get-access", {
        username: encEmail,
        password: encMobile
    })
}
Impact:

Admin panel fully open to brute force. On success: access to admin_api/Get_eAdmitCard/ for all candidates, full document download, admit card generation.

🟠 High Severity Findings #

V-06 CVSS 8.6

HMAC Request Signing — Fully Exposed

The API Gateway used HMAC-SHA512 to sign all requests. The signing algorithm and all its secret components were fully retrievable from the client JS bundle. 

// Algorithm exposed in full:
SecretKey = SHA512(HMAC_SALT + timestamp + SECRET_UUID)
// Where:
HMAC_SALT = "rz8LuOtFBXphj9WQfvFA"
SECRET_UUID = "C4A29052-0500-4361-9A3C-BD4B9B7*****"
TIMESTAMP_FORMAT = "DDMMYYYYHHMMSS" (UTC)
Impact:

Any attacker could generate valid HMAC-signed requests to any API endpoint — bypassing the primary authentication layer for all backend services.

V-07 CVSS 8.4

UDID Disability Card API Credentials Exposed

The portal integrated with UDID (Unique Disability ID) to verify physically challenged candidates' disability status. Credentials for this API were hardcoded: 

UDID_CLIENT_ID:     4fb711bb4c24db070da4e8b6********
UDID_CLIENT_SECRET: c63884422c269a584fc6b0f9********
API: https://swavlambancard.gov.in/api/getApplicationInformation/
Impact:

The API response on test call returned "Your IP is not whitelisted" — indicating IP restrictions were the only secondary protection layer.

V-08 CVSS 8.2

OTP Trigger Without Authentication

The mobile login flow allowed triggering an OTP SMS to **any registered mobile number** with zero authentication. Additionally, deviceToken was static ("device-info"), indicating absence of real client fingerprinting controls. 

// Request:
POST /ngrp_api/authentication/User/V1/MobileLogin/validate_User
Body: { "deviceToken": "device-info", "mobileNo": "XXXXXXXXXX" }

// Confirmed response:
{
  "status": true,
  "message": "OTP has been sent to registered mobile number",
  "response": {
    "tempId": "6a1ffe3ed5b037d354e40e52",
    "txnId": "6a1ffe3ed5b037d354e40e52"
  }
}
Impact:

OTP flood/spam attack on any registered candidate's mobile number. Could be used to harass or disrupt candidates before exam dates.

V-09 CVSS 7.5

Unauthenticated User Enumeration via Search API

Two search endpoints confirmed whether a mobile number or email was registered — without any session verification context:

Endpoint Input Registered Response Unregistered Response
onboarding/V1/Search/MobileNo Mobile number "Mobile No. is already registered" false
onboarding/V1/Search/EmailId Email address "Email ID is already registered" "not registered"
Impact:

An attacker could scrape mobile number databases and enumerate which candidates are registered on the UPSC portal — leaking registration statuses.

V-10 CVSS 7.2

Firebase Full Configuration Exposed

Complete Firebase project configuration was found hardcoded inside the frontend JS bundle. 

apiKey:           AIzaSyDRuNakzmVTaeom8LMLmTTox********
projectId:        ndrp-35433
storageBucket:    ndrp-35433.appspot.com
messagingSenderId: 682184681654
appId:            1:682184681654:web:a4261be8c68243d8be5e17
VAPID Key:        BEZNt1hE9Ra9Y7PE9np_NJ7GzH**************
Impact:

The VAPID key allows sending push notifications to all subscribed users. If Firebase Storage/Database security rules were misconfigured, unauthorized access to databases was possible.

V-11 CVSS 7.0

Password Hashing Algorithm Fully Client-Side

The complete password hashing algorithm was visible in the JS bundle. Since the saltkey retrieval endpoint was unauthenticated, password hashes could be prepared directly client-side. 

// Hashing pipeline:
const step1 = CryptoJS.SHA512(password).toString(CryptoJS.enc.Hex);
const step2 = step1 + serverSalt;
const step3 = CryptoJS.SHA512(step2).toString(CryptoJS.enc.Hex);
const finalHash = btoa(unescape(step3));
Impact:

Offline hash computation against known password dictionaries became trivial with the logic exposed.

V-12 CVSS 6.8

JWT Token Stored in sessionStorage

Login tokens (JWT) were stored in sessionStorage under the key userData — directly accessible to any script running in the browser context. 

// On login:
sessionStorage.setItem("userData", JSON.stringify(tokenObject));

// On page load:
const user = JSON.parse(sessionStorage.getItem("userData"));
Impact:

Any cross-site scripting (XSS) vulnerability on the domain could lead to immediate session hijacking and UI guard bypasses.

✅ Remediation Confirmed #

All 15+ findings are patched. Specific fixes observed on the production target:

  • RSA private key removed from client bundle — encryption now server-side only.
  • OAuth secrets rotated and moved to secure backend configurations.
  • Rate limiting controls integrated on admin login, OTP, and candidate lookup search endpoints.
  • IDOR resolved with robust identity verification filters on all profile routes.
  • Firebase credentials restricted with stricter security rules.
  • HMAC sign routines migrated to private backend APIs.

💡 Key Takeaways for Developers #

1

Never ship private keys in frontend code

Sensitive cryptographic keys belong strictly behind server configurations. Obfuscating is not encrypting.

2

OAuth client secrets belong in backends

A client-side bundle cannot hide credentials. Treat anything sent to the browser as public information.

3

Rate limit everything

Verification routes, login endpoints, search boxes, and OTP triggers must use CAPTCHA and request throttling.

4

Authorization is different from Authentication

A valid session token shouldn't grant full database access. Always enforce object-level ownership checks server-side.

5

sessionStorage is not a secure token store

Keep JWT session markers in httpOnly cookies to prevent extraction by cross-site scripting scripts.
